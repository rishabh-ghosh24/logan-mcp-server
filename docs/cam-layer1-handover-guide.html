2. What the security boundary enforces

IdentityEach CAM receives a unique SSH key and a unique CAM id.
ScopeThe server stores the CAM's approved customer numbers and resolved entity names in a root-owned policy.
ConnectionThe key can enter only the forced Logan MCP command as the restricted cam account.
Fail closedA missing or invalid entity snapshot denies startup; the CAM runtime never falls back to listing the tenancy.

The policy lives at /etc/logan-mcp/access_control.yaml. Runtime code, policy, immutable configuration, launcher, and managed authorized_keys are root-owned. Password login, PTY allocation, forwarding, tunnelling, user RC files, arbitrary remote commands, SCP, and SFTP are disabled for the restricted account.

The CAM sees only their configured resolved_entities. Allowed queries are automatically constrained to those entities. An explicit request for another customer returns ENTITY_ACCESS_DENIED and tells the user to contact an administrator. A genuine zero-log response therefore means the allowed query ran but found no matching data.

Never give a CAM regular VM credentials A regular Linux account with sufficient file or sudo access sits outside this boundary. CAM users must receive only the generated restricted bundle. Administrator SSH credentials and CAM credentials must remain separate.

3. Operating runbooks grouped by OS

Use this section for the normal handoff. The Linux VM always runs the root-owned runtime under /opt/logan-mcp. Administrator MCP access is named assurance-logan-admin; restricted CAM access is named assurance-logan. Both use the same latest runtime, but they deliberately use different credentials and launchers.

Do not reuse the CAM connection as an administrator connection assurance-logan-admin uses an individual Linux administrator login plus the protected admin-launch command. assurance-logan uses the recipient's forced-command CAM key. Keeping the names separate prevents an unrestricted administrator credential from being mistaken for a CAM credential.

A. Linux server + macOS/Linux administrator workstation

A1. Existing platform administrator: authorize an MCP administrator

Replace iustin with the person's actual Linux login and iustin.dorila with the permanent audited administrator id.

sudo visudo -f /etc/sudoers.d/assurance-logan-iustin

Insert this identity-pinned rule:

Cmnd_Alias ASSURANCE_LOGAN_IUSTIN = /opt/logan-mcp/bin/admin-launch iustin.dorila, /opt/logan-mcp/bin/cam-admin *
iustin ALL=(root) NOPASSWD: ASSURANCE_LOGAN_IUSTIN
sudo visudo -cf /etc/sudoers.d/assurance-logan-iustin
sudo /opt/logan-mcp/bin/cam-admin bootstrap-check --json

Require valid sudoers syntax and SUCCESS. The exact admin-launch iustin.dorila rule prevents the administrator from selecting a different audit identity.

A2. Administrator: configure Codex on macOS or Linux

Configure automation1 in ~/.ssh/config with the administrator's individual SSH key and pinned host verification:

Host automation1
    HostName 130.162.53.112
    User iustin
    IdentityFile ~/.ssh/<individual-admin-key>
    IdentitiesOnly yes
    BatchMode yes
    StrictHostKeyChecking yes
    UserKnownHostsFile ~/.ssh/known_hosts
    ServerAliveInterval 60
    ServerAliveCountMax 3

Add this table to ~/.codex/config.toml:

[mcp_servers.assurance-logan-admin]
command = "ssh"
args = ["-T", "-o", "BatchMode=yes", "automation1", "sudo", "-n", "/opt/logan-mcp/bin/admin-launch", "iustin.dorila"]

Restart Codex, run codex mcp list, and test with:

Use only the assurance-logan-admin MCP server. Test the connection and list the available administrator tools.

4. Add another Assurance Logan administrator

Use an individual Linux account, an individual SSH key, and one permanent audited administrator id. Never share the opc key or place an administrator key in the restricted cam account.

  1. Create or identify the person's normal Linux login through the organization's VM access process.
  2. Choose the audited id, normally firstname.lastname.
  3. Create an identity-specific sudoers rule. Do not wildcard admin-launch, because that would allow selection of another audit identity.
sudo visudo -f /etc/sudoers.d/assurance-logan-<linux-login>

Example for Linux login iustin and audited id iustin.dorila:

Cmnd_Alias ASSURANCE_LOGAN_IUSTIN = /opt/logan-mcp/bin/admin-launch iustin.dorila, /opt/logan-mcp/bin/cam-admin *
iustin ALL=(root) NOPASSWD: ASSURANCE_LOGAN_IUSTIN
  1. Validate the rule and have the administrator confirm their approved commands.
sudo visudo -cf /etc/sudoers.d/assurance-logan-<linux-login>
sudo -l
sudo /opt/logan-mcp/bin/cam-admin bootstrap-check --json

Require SUCCESS. Configure the local assurance-logan-admin table using section 3. Runtime deployment/bootstrap remains a separate full platform-administrator capability.

4. Add another CAM administrator

Use an individual Linux account and individual SSH key. Do not share the opc key and do not place an administrator's key in the restricted cam account.

  1. Create or identify the administrator's normal Linux login according to the organization's VM access process.
  2. As an existing full administrator, add a dedicated least-privilege group and the administrator to it.
ADMIN_USER=<linux-login>
sudo groupadd --force logan-cam-admins
sudo usermod -aG logan-cam-admins "$ADMIN_USER"

Create /etc/sudoers.d/logan-cam-admins with visudocam-admin parser is the administrative boundary for these operations.

sudo visudo -f /etc/sudoers.d/logan-cam-admins

Insert:

%logan-cam-admins ALL=(root) NOPASSWD: /opt/logan-mcp/bin/cam-admin *
  1. Validate the sudoers file and have the new administrator start a fresh login session so group membership is refreshed.
sudo visudo -cf /etc/sudoers.d/logan-cam-admins
id
sudo -l
sudo /opt/logan-mcp/bin/cam-admin bootstrap-check --json

Require SUCCESS from bootstrap-check. If the person also needs to deploy or bootstrap runtime code, approve that as a separate platform-administrator capability; do not broaden this sudo rule casually.

The example below creates a new CAM named jane.doe with access to customers 176 and 174. Replace those values for the approved request.

8. Validate and securely deliver the bundle

Provisioning already creates both the directory and ZIP:

logan-cam-jane.doe/
├── logan-cam.key
├── Install-Logan-MCP.command
├── Double-Click-to-Install.cmd
├── Install-Logan-MCP.ps1
└── README.html

logan-cam-jane.doe.zip

macOS validation

ZIP="$HOME/logan-cam-bundles/logan-cam-jane.doe.zip"
unzip -t "$ZIP"

if unzip -l "$ZIP" | grep -q '__MACOSX/'; then
  zip -d "$ZIP" '__MACOSX/*'
fi

shasum -a 256 "$ZIP"

Windows validation

$Zip = "$HOME\logan-cam-bundles\logan-cam-jane.doe.zip"
Get-FileHash -Algorithm SHA256 $Zip
tar -tf $Zip
  • The archive test succeeds and contains only the five expected files.
  • The recorded SHA-256 belongs to the final ZIP being delivered.
  • The live verify result matches the approved CAM id, customers, fingerprint, and resolved entities.
  • The transfer is authenticated, recipient-specific, access-logged, and expires within seven days.
  • The private bundle is not sent by email, ordinary chat, or a broadly shared folder.
What the checksum does SHA-256 does not encrypt the ZIP. It lets the administrator and recipient prove they have the identical archive and detects corruption or replacement. A recipient-specific secured SharePoint transfer is suitable when it follows the organization's approved credential-transfer policy; use Slack only if the organization's security policy explicitly approves it for bearer credentials.

11. CAM acceptance test

Run these as separate prompts in a new Codex task. Tell Codex to use only the restricted server so results cannot come from an unrestricted Logan connection.

A. Connection

Use only the assurance-logan MCP server. Test the connection.

B. Allowed entities

Use only the assurance-logan MCP server. List every entity I am allowed to access.

Expect only the entities approved in the server-side CAM assignment.

C. Allowed data

Use only the assurance-logan MCP server. Show all logs from the last 7 days grouped by log source.

The result is scoped to the allowed entities even if generated prose incorrectly says “entire tenancy.” Judge enforcement by the returned entities and server behavior, not that phrase.

D. Denied customer

Use only the assurance-logan MCP server. Show the same 7-day log data for Customer114_Network_Rail_Infrastructure_Limited.

Expect a clear access-restricted response, the permitted entity names, and advice to contact the Assurance Logan administrator. Do not accept a plain “0 logs” response for an explicitly unauthorized entity.

Acceptance passes only when all four checks passConnection succeeds, the entity list is exact, allowed data is returned within scope, and the unauthorized entity is explicitly denied.

12. Change scope, refresh entities, or revoke access

Show and verify without mutation

ssh automation1 \
  'sudo /opt/logan-mcp/bin/cam-admin show --cam <cam-id> --json'

ssh automation1 \
  'sudo /opt/logan-mcp/bin/cam-admin verify --cam <cam-id> --json'

Refresh an older or intentionally changed entity snapshot

ssh automation1 \
  'sudo /opt/logan-mcp/bin/cam-admin verify --cam <cam-id> --refresh-policy --json'

This backup-aware operation updates resolved_entities but does not change the key. Use it for older records missing a snapshot or after an approved customer entity-inventory change.

Change customer scope or delivery permission

Do not hand-edit /etc/logan-mcp/access_control.yaml or /home/cam/.ssh/authorized_keys. Record the approval, deprovision the existing CAM, provision the complete new scope with a new key, verify it, and securely deliver the replacement bundle.

Deprovision

On macOS:

./cam-setup/admin/macos/Deprovision-Logan-CAM.command \
  --cam <cam-id> \
  --ssh-target automation1

On Windows, double-click cam-setup\admin\windows\Deprovision-Logan-CAM.cmd, or run:

.\cam-setup\admin\windows\Deprovision-Logan-CAM.ps1 `
  -CamId "<cam-id>" `
  -SshTarget "automation1"

The wrapper shows the current assignment and requires the exact confirmation REVOKE <cam-id>. Successful revocation removes the policy and key, terminates that CAM's processes, and proves the old key cannot authenticate.

StatusRequired action
SUCCESSAccess is verified revoked. Record the result.
FAILED_ACCESS_REVOKED_CLEANUP_REQUIREDAccess is revoked, but cleanup remains. Use the printed recovery metadata; never restore the old key.
FAILED_REVOCATION_UNCONFIRMEDTreat the key as active. Run the exact printed manual command immediately and escalate.

Ordinary deprovisioning intentionally retains audit history, saved and learned queries, learning inputs, useful preferences, reports, delivery metadata, and compliance evidence. Archival is a separate future operation.

14. Operational records and recovery

Record for every authorization change

  • Request and approving authority
  • CAM id and approved customer numbers
  • allow_delivery value
  • Resolved entity names
  • Public key fingerprint — never the private key
  • Release/deployed runtime revision
  • Final ZIP SHA-256 and secure delivery channel
  • Provision, verify, acceptance, scope-change, and deprovision outcomes

Recovery rules

  • Treat a lost, copied, or misdelivered bundle as a compromised bearer credential. Deprovision immediately and issue a new key.
  • Use the root-owned backup path printed by cam-admin only for deliberate recovery.
  • Never restore a deprovisioned key or an old authorized_keys file to clear an error.
  • After recovery, rerun bootstrap-check, then show or verify, and record the evidence.
